# agents.md — life_coach_frontend

Orientation for an AI agent (or a new human engineer) picking up work in
this repo. Read this before making changes.

## What this is

Flutter client for "Cosmic Coach," talking to the `life_coach_backend`
FastAPI service. Three core screens: auth (Screen 1), home (Screen 2 —
voice/chat toggle over an animated starfield), and a floating menu
(Screen 3, includes the Vedic profile chart). Design source of truth is
the "Cosmic Coach" HTML mockup the product owner supplied; UI work should
match its spacing/animation timing constants where a screen references it.

## Architecture

```
widgets (View)  ──watch/read──>  ViewModel (Riverpod AsyncNotifier)  ──>  Repository  ──>  Dio (REST) / SseClient (SSE)  ──>  backend
                                                                                                  |
                                                                                          FirebaseAuth ID token
                                                                                          attached per-request
```

- **State management: Riverpod is the default for everything.** `Bloc` is
  used ONLY for `ChatBloc` and `VoiceCubit` (`lib/features/home/bloc/`) —
  an explicitly agreed architecture boundary, because chat/voice are
  genuinely event-stream-shaped (SSE chunks, speech-recognizer callbacks)
  in a way `AsyncNotifier` models awkwardly. Do not introduce a third Bloc
  for anything else; do not convert the existing two to Riverpod without
  discussing it first.
- **Repository pattern**: one repository per feature
  (`features/*/repository/`), each built from the shared `dioProvider` /
  `sseClientProvider` (`core/api/api_providers.dart`). Widgets never touch
  `Dio` directly.
- **ViewModel pattern**: one `AsyncNotifier<T>` per feature
  (`features/*/view_model/`) exposing a single `AsyncValue` the view
  watches. `AsyncData(null)` is a valid *state* (e.g. "no profile saved
  yet"), not an error — don't conflate the two when adding new ViewModels.
- **Routing**: `go_router`, all routes declared in
  `core/router/app_router.dart` under the `Routes` class — never hardcode
  a path string in a widget. The redirect callback is the single source of
  truth for the signed-in/signed-out gate.
- **Theming**: `context.cosmic` (`CosmicTokens`, `core/theme/cosmic_theme.dart`)
  is the only place colors/gradients should come from — no raw `Color(0x...)`
  literals in feature widgets except where the token doesn't exist yet
  (extend `CosmicTokens` instead of hardcoding).
- **Logging**: `appLogger` (`core/logging/app_logger.dart`, wraps the
  `logger` package). Never `print` — `avoid_print` is a lint error.
- **Analytics**: `AnalyticsService` (`core/analytics/analytics_service.dart`)
  is the only thing that imports `firebase_analytics`. See
  `docs/analytics-events.md` for the event catalog and how to add a new
  one. It never throws, even with no Firebase app configured, so it's safe
  to construct a default instance in tests.

## Config

Backend URL is injected at build time, never hardcoded:

```bash
flutter run --dart-define-from-file=config/dev.json       # emulator
flutter run --dart-define-from-file=config/local.json     # physical device (create from dev.json, gitignored)
flutter run --dart-define-from-file=config/staging.json
flutter run --dart-define-from-file=config/prod.json
```

See `docs/environment-config.md`. `lib/core/api/api_client.dart`'s
`apiBaseUrl` has no fallback on purpose — a missing `--dart-define` flag
must fail loudly (every request errors + a logged warning), not silently
hit a stale developer IP.

`lib/firebase_options.dart` is generated by `flutterfire configure` — if
it's ever missing/stale, that's the command to regenerate it, not a file
to hand-edit.

## Testing

`flutter_test` + `bloc_test` + `mocktail`. Pattern: mock the repository
(`class MockXRepository extends Mock implements XRepository {}`), inject
it into the Bloc/ViewModel under test, assert on emitted states — see
`test/chat_bloc_test.dart` for the fullest example (including how
`MockAnalyticsService` is verified for event side effects).

```bash
flutter test
```

**Important limitation on this project as of now:** development on this
repo has been happening in a sandbox with no Flutter SDK installed and no
network access to fetch one. Every Dart change in this repo's history was
written and reviewed as text (structure, syntax, import correctness,
brace/paren balance checked programmatically) but **never actually
compiled or run** in that environment. If you have real Flutter tooling
available, your first move on any inherited branch should be
`flutter pub get && flutter analyze && flutter test` — treat anything
merged without that having been possible as reviewed-but-unverified.

## Known asset gaps

- `assets/icon/app_icon.png` (app launcher icon) and the splash assets
  under `assets/splash/` are placeholder abstract gold-ring artwork
  generated in-session, NOT the user's real logo — no source logo file
  was ever actually supplied despite being referenced in the original
  bug report. Swap in the real asset, then re-run
  `dart run flutter_launcher_icons` and
  `dart run flutter_native_splash:create`.
- The Om glyph ("ॐ") is rendered live via `GoogleFonts.notoSerifDevanagari`
  at runtime, which is fine on a real device with network access to fetch
  the font. It was deliberately NOT baked into any static image asset in
  this sandbox, since no Devanagari-capable font was installable/fetchable
  here — attempting to approximate the sacred glyph programmatically for a
  static PNG was judged worse than leaving it as live text.

## Branch & commit workflow

Same convention as the backend repo: `dev` is the integration branch, one
branch per bug/feature off `dev`, PR per bug — never commit to `main`
directly. Branch naming: `bugfix/<short-description>` /
`feat/<short-description>`. Commit messages: Conventional-Commits subject,
body explaining *why*, footer naming the branch — match the tone of
existing commits on `dev`.

## Working in this sandbox environment (if you're an agent in Cowork)

Same gotchas as the backend repo (see its `agents.md` if both are
available), most importantly:

1. The mounted repo's `unlink()` is broken (`EPERM` on every file) but
   `rename()` works. Do branch/checkout work in a scratch clone on a
   normal filesystem, then push finished branches into the mounted repo
   with `git fetch <scratch-clone-path> refs/heads/<branch>:refs/heads/<branch>`.
2. Write commit messages with backticks to a file and commit via
   `git commit -F <file>` — a shell heredoc will mangle backticks as
   command substitution otherwise.
3. Because branches share a working tree in a scratch clone, always
   `git status --short` before committing to catch stray untracked files
   left over from a previous branch's checkout bleeding into the current
   one (this repo's history has hit this at least once — a leftover
   `app_icon.png` almost got committed to the wrong branch).
